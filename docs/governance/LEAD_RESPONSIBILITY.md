# Lead Responsibility

The Lead owns one accepted main spine, independent semantic/evidence review and authorized integration. AGENTS owns product/privacy constraints; this file owns the working method and role. GitHub/current entries remain authority, not another task database.

## Takeover and current responsibility

For a trustworthy focused handoff, verify live main, affected issue/PR/head, ownership, applicable gate and decision-changing delta. Full integration/release/major takeover or a concrete cross-lane conflict requires the relevant full view: priority work, PRs/writers, accepted-not-integrated candidates, blockers, support, next authority and closure debt. No separate checksum form or unrelated full scan. Verify HEAD once, refresh before writes or changed-state decisions.

Complete the requested responsibility, including necessary callers, compatibility, tests and recovery. Prefer adequate existing code/knowledge/native capabilities. Additional reads/checks/tests/audits/agents need a concrete gap whose result can change action, implementation, source, safety, rollback or acceptance; no counters, command-purpose forms or evidence ledger.

## Evidence and completion

Reuse still-valid final-state proof. Revalidate only for relevant change, direct contradiction, scope mismatch, unmet acceptance or an applicable required check. Required executable exact-head CI is not replaced by old results. Separate code, synthetic tests, browser/runtime/transport and authorized production-write claims.

When evidence and authority suffice, review actual identity/diff/semantics/tests, perform the allowed expected-head GitHub action and update only materially changed owning facts. Handle actual source-issue, dependent/overlapping-lane, evidence/blocker, regression, release and retirement effects; do not mechanically fill every field after every merge. A next lane requires a real authorized goal. Stop when result and necessary acceptance exist with no in-scope blocker; no reassurance audit or docs-only SHA chase. The user is not a message bus.

## Existing canonical states

LANE_STATE: ACTIVE|HOLD|BLOCKED|QUEUED|DEFERRED|RETIRED. CANDIDATE_STATE: NONE|LOCAL_CANDIDATE|REMOTE_REVIEWABLE|SEMANTICALLY_ACCEPTABLE_PENDING_GATES|CHECKPOINT_ACCEPTED|ACCEPTED_INTEGRATED|SUPERSEDED|REJECTED. LEADER_DECISION: NO_ACTION|ACCEPT|RETURN|BLOCK|QUEUE|MERGE|CLOSE|ABANDON|NEEDS_HUMAN. These existing collaboration fields are not a new runtime or small-repository template.

## Authority inheritance and escalation

Necessary actions inherit an authorized bounded plan while objects, risk, goal and rollback remain unchanged. Escalate new dangerous/destructive production/data scope, stronger deletion/overwrite, failed rollback, new goal/support promise, secret/privilege relaxation, CI bypass, admin/billing expansion or release-policy change. No governance cleanup grants these rights or bypasses the product's per-run confirmation, exact-input, idempotency or mutation gate. Preserve applicable trusted source, secrets, integrity, version/role, backup/rollback and real-result acceptance.

## Governance evolution

EXECUTION_DEFECT fixes execution; KNOWLEDGE_GAP fixes owning knowledge/navigation; GOVERNANCE_GAP amends the existing rule for a recurring uncovered boundary; TOOLING_GAP prefers a cheap stable tool/template/CI improvement. The first two do not create more rules.

A lasting rule needs the nearest real Bad/Good pair differing by one decisive fact, trigger, changed decision, satisfaction/stop and replacement in the PR/issue. Remove/merge duplicates in the same change; new governance files need an independent responsibility/consumer existing owners cannot serve. Active applicable rules execute; repeated misses improve entry/dispatch/tools rather than add reminders. Add coordination or risk controls only when actual collaboration/risk needs them, not to complete a template.
